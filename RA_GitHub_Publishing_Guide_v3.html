RETAIL ANNUITIES / PUBLISHING PLAYBOOK

Put the roadmap on GitHub Pages

A browser-based setup for a shared team URL, with a privacy check before any internal portfolio data goes live.

Prepared for portal v3. GitHub documentation checked November 24, 2026. Actual menus and available features depend on your company account and administrator policies.

Do not start by making this site public.

The portal is marked for Home Office use only. Its HTML includes the roadmap data, PMO documents and reference assets, even when a particular tab is hidden. A private repository does not automatically make the published website private. Establish the website's access controls before uploading the real portal. [6]

1. Confirm the hosting arrangement with IT

Ask your GitHub administrator to confirm that your company permits this data on GitHub and supports private GitHub Pages. On GitHub.com, private Pages requires an organization using GitHub Enterprise Cloud, and an organization-owned private or internal project repository. Team members need read access to the publishing repository. Enterprise Managed Users have additional enterprise-only access restrictions. [1]

Recommended setup: a private repository in the company organization, a privately published Pages site, read access for the relevant team and write access only for the maintainers. Ask the organization owner to permit private Pages and disallow public Pages for this use case. Organization controls are under Settings > Member privileges > Pages creation. [3] [9]

Stop when private Pages is not available. Do not change the repository or website to public to bypass a plan or policy restriction. IT can instead keep the code in an approved private GitHub repository and deploy the website to an approved company host with its own access controls. The packaged Python shared host is a separate deployment option, not a GitHub Pages component.

2. Create a repository and upload only the privacy-check page

  1. Sign in to the approved company GitHub account. Choose New repository, and select the company organization as the owner.
  2. Use a project name such as ra-roadmap-portal. Select Private. A README is optional. Do not create an organization-wide ORG.github.io site for this private project-site setup. [1] [6]
  3. Extract RA_GitHub_Publishing_v3.zip. Open 01-privacy-check. It contains a non-sensitive index.html and a .nojekyll marker. It contains no portfolio or PMO data.
  4. In the repository, choose Add file > Upload files. Upload the contents of 01-privacy-check to the repository root. Do not upload the ZIP or its outer folder. [5]
  5. Use a commit message such as Add access-check landing page. Commit to main when company policy permits; otherwise use a new branch and an approved pull request, then merge it into the publishing branch. Follow any protected-branch rules rather than disabling them. [5]

The root should now contain the following files. A README can also be present.

ra-roadmap-portal/
  index.html       <-- privacy-check page only, for now
  .nojekyll

3. Enable Pages, then verify private visibility

  1. Open the repository's Settings, then Pages under Code, planning, and automation.
  2. Under Build and deployment, set Source to Deploy from a branch.
  3. Select branch main, folder /(root), and choose Save. Branch publication deploys changes from that folder. [4]
  4. Under GitHub Pages visibility, choose Private. Repository-admin permissions are needed to change website visibility. When the control is absent, ask your administrator to resolve eligibility or policy before proceeding. [2]
  5. Review the Pages build/deployment in Actions. After it succeeds, return to Settings > Pages and use Visit site. [4] [6]
Access check before real data

Open the test page as an authorized team member. Then test the same address in a signed-out/private browser and, where practical, with an account that lacks repository access. The unauthorized viewer must not receive the test-page content. A sign-in prompt or access-denied response is appropriate. Have IT confirm that the actual Pages visibility is Private; a failed browser test alone is not proof of correct configuration.

Use the URL shown by Visit site. Private Pages sites use a distinct automatically assigned subdomain; do not assume that a standard public ORG.github.io/repository address is the correct private URL. [1]

4. Replace the test page with the real portal

Proceed only after the access check passes. In the GitHub publishing ZIP, open 02-portal. Its index.html is the full v3 website, already named for Pages. The file is self-contained: the four PMO documents and their previews are embedded, so no asset-folder upload is needed for this version.

Use Add file > Upload files again and upload this real index.html to the same repository root, replacing the test page. Leave .nojekyll in place. Commit the change, or merge the approved pull request. The HTML is approximately 10 MB, below GitHub's current 25 MiB browser-upload limit. Future embedded attachments may increase its size. [5]

After the deployment succeeds, reopen the Pages URL. Confirm that Executive summary is the landing view, the project cards show the expected approved snapshot, the project timelines and deep links open correctly, and PMO files download. Repeat the unauthorized-access check. Keep the source code, backups and shared-host state outside the published folder; only the intended website should be published.

5. Give the team access and share the right URL

A repository administrator can grant the appropriate GitHub team read access in the repository's access settings. Grant write access only to the people responsible for publishing changes. Privately published Pages uses repository read access for its viewers. [9] [1]

Share the Pages website URL from Visit site, not the repository's github.com code-view address and not a file:/// link from your computer. Open a project on the hosted website and use Copy link to get a team-usable project deep link. The portal uses hash routes, so project links do not require special server routing.

6. Publish future edits or document-driven updates

This is the workflow implemented in v3:

Open the latest portal
  > Edit mode
  > Make edits, or Update from file
  > Review proposed file changes and apply them
  > Manage content > Export index.html
  > Replace index.html in the same repository folder
  > Commit / approve and merge
  > Confirm successful Pages deployment
  > Team opens the same website URL

Supported file updates remain the established integrated PowerPoint layout, structured Word/PowerPoint tables, CSV and supported JSON updates. Unsupported or ambiguous content is not guessed. The unchanged original PowerPoint produces no proposed changes in the delivered baseline. An upload to PMO documents adds a repository document; it is different from Update from file, which refreshes roadmap records after review.

What is automatic, and what is not

GitHub Pages republishes committed changes from its configured source. It is a static HTML/CSS/JavaScript host, not a shared writable application backend. Saving a portal draft, uploading a document in the browser or putting a PPTX into the GitHub repository does not write the new portfolio back to GitHub or automatically parse that repository document. Export and commit the updated HTML to publish it. [4] [7]

The Edit mode control is not a login or an authorization boundary. A viewer can edit their own local copy, but that does not change the shared site. Repository permissions and the publishing process control updates to the site. Never add a personal access token, editor key, password or other secret to the HTML, JSON, repository files or a URL. [5]

For browser-based shared writes without exporting, use the separate shared-host package behind company authentication and HTTPS. Its Python service and APIs do not run on GitHub Pages. It has not been deployed or connected to your company environment.

7. Common problems and recovery

ProblemWhat to check
Pages or Private is not offeredConfirm plan, organization ownership, admin permissions and company Pages policy. Do not switch the confidential site to Public. [1] [2]
The website gives 404Check that lowercase index.html is at the top level of the selected branch/folder, not nested under 02-portal. Confirm the deployment succeeded and use the current Visit site address. [8]
I see code instead of the portalYou may be on the repository's file-view page, not its Pages website. Use Settings > Pages > Visit site. [6]
Teammate cannot open the private siteConfirm they are signed in with the approved account, satisfy company identity rules and have repository read access. [1]
I edited the page, but others see the old versionBrowser drafts are local. Export index.html, upload it to the configured publishing source, commit/merge and check the deployment. Reload the site after success. Browser caching can also affect the view. [4] [8]
Numbers still say November 3The reporting date is the approved portfolio snapshot, not today's date. Update data and reporting date together; the portal does not mark projects complete merely because time has passed.
A publication was wrongKeep an approved previous HTML and JSON backup. Re-upload the prior HTML as index.html, or have the maintainer restore the known-good file through the team's Git history process, then deploy again. Do not delete the private site merely to roll back content.

8. Files, maintenance and handover

GitHub publishing ZIP: 01-privacy-check is the non-sensitive setup page; 02-portal is the real website. Upload only the contents of the appropriate folder at the appropriate stage.

Complete editable ZIP: the root index.html is the real website; Editable source contains the unminified modules, JSON data, assets and builder; PMO documents contains the original four files. For code-level changes, run python "Editable source/build.py" from the extracted package root, then publish the rebuilt root index.html. Normal content maintenance does not require coding.

Handover checklist: named website owner; approved private repository and website; reader and editor access confirmed; successful authorized and unauthorized access tests; agreed publication approval; previous-version backup; current reporting-date owner.
